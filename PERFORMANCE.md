# Performance profiling & optimization

A senior-performance-engineer pass over the Adaptive AI Learning Platform:
**profile first, then optimize only where the evidence shows a bottleneck.**

All numbers below come from a reproducible harness ([`perf/profile.mjs`](perf/profile.mjs))
run against a real PostgreSQL 18 instance seeded with a realistic mid-size
tenant, using `EXPLAIN (ANALYZE, BUFFERS)` for plans and 30-sample wall-clock
timings (p50/p95) for latency.

## Methodology

- **Dataset** (one mid-size tenant, generated by the harness):

  | table | rows |
  |-------|------|
  | assessments | 1,800 |
  | assessment_items | 14,400 |
  | mastery_states | 4,800 |
  | activity_events | 30,000 |
  | recommendations | 3,600 |
  | learning_paths | 600 |
  | questions | 900 · skills 60 · students 600 |

- **How to reproduce:**
  ```bash
  npm i --no-save embedded-postgres   # transient dev-only dependency
  node perf/profile.mjs
  ```
  The harness boots an ephemeral Postgres, pushes the Drizzle schema, seeds the
  data, then measures each workload **before and after** the candidate change on
  the *same data / same instance* (indexes are dropped for the baseline and
  created for the "after" phase) so every comparison is like-for-like.

- **In production**, the observability layer already exposes the live equivalents
  (`adaptiq_db_query_duration_seconds`, `adaptiq_http_request_duration_seconds`,
  `adaptiq_db_pool_connections`) so these wins are verifiable on real traffic.

## What was profiled

Database queries · N+1 · API/server-render latency · client rendering ·
unnecessary requests · large payloads · repeated ML calculations ·
recommendation generation · question selection · indexes · connection pooling.

### Findings & verdicts

| Area | Verdict | Evidence |
|------|---------|----------|
| Missing indexes on `student_id`/status/recency filters | **BOTTLENECK — fixed** | Seq Scans on `assessments`, `activity_events` (30k), `learning_paths`, `recommendations` |
| `getCohortSnapshot` loads 4 whole tables into JS | **BOTTLENECK — fixed** | 43ms/req, grows linearly with tenant; on dashboard **and** analytics |
| `getQuestionBankAnalytics` materializes the whole bank + a thrown-away item group-by, and the route calls it **twice** | **BOTTLENECK — fixed** | 10ms/req, heavy query run 2× per request |
| `loadClassifier` hits the DB ~2×/answer for stable data | **WASTE — fixed** | 2 round trips per answer on the hottest path |
| Engine re-queries mastery via `loadSkillFeatures` on every item served | **REDUNDANT QUERY — fixed** | 2 extra queries per question, value already in memory |
| Connection pool unconfigured (pg default max=10, no acquire timeout) | **RISK — hardened** | no timeout ⇒ a stuck connection can hang a request |
| Client rendering / polling / unnecessary requests | **No action** | dashboards are server components; no `setInterval`, no client fetch loops |
| N+1 in the query layer | **No action** | already batched (`inArray` + `Promise.all` + lookup maps) |
| Question-selection algorithm compute | **No action** | in-memory scoring over a bounded candidate pool; DB I/O was the cost, now addressed |

## Optimizations & measurements

### 1. Indexes for frequently-queried fields

Added to `src/db/schema.ts` (applied via `drizzle-kit push`):

| Index | Serves |
|-------|--------|
| `assessments (student_id)` | learner history / engine lookups |
| `assessments (student_id, status)` | "completed" performance queries |
| `activity_events (student_id, created_at desc)` | learner activity feed |
| `activity_events (created_at desc)` | platform-wide feed |
| `learning_paths (student_id)` | learner paths |
| `recommendations (student_id, status)` | recommendation queue (replaces the plain `student_id` index) |
| `assessment_items (question_id)` | item analytics / calibration |

**Before → after (p50 wall-clock; EXPLAIN exec in parentheses):**

| Query | Before | After | Speedup | Plan change |
|-------|--------|-------|---------|-------------|
| `listAssessments(student)` | 0.79ms | 0.54ms | **1.5×** | Seq Scan → Index Scan |
| `getStudentPerformance(completed)` | 0.58ms (0.14ms) | 0.28ms (0.02ms) | **2.1×** (7×) | Seq Scan → index-only |
| `getActivity(student)` | 2.33ms (4.04ms) | 0.67ms (0.09ms) | **3.5×** (**45×**) | Seq Scan(30k) → Index Scan |
| `getPaths(student)` | 0.39ms | 0.29ms | 1.3× | Seq Scan → Index Scan |
| `getRecommendations(student,status)` | 0.85ms | 0.36ms | **2.4×** | Seq Scan → Index Scan |

The EXPLAIN exec-time gaps (e.g. `getActivity` **45×**) are the pure-DB win; the
p50 gaps are smaller because they include driver/JS overhead. The absolute p50s
are small at this scale — the point is that the **Seq Scans are eliminated**, so
these queries stay flat instead of degrading linearly as each learner's history
grows.

### 2. `getCohortSnapshot` → SQL aggregates — **20.8× faster**

Was: `SELECT *` from `mastery_states`, `assessments`, `recommendations`,
`learning_paths` (whole tables) then count/average in JS. Now: scalar counts run
as tenant-scoped SQL aggregates (`count(*) filter (...)`, `avg(...)`), and only
`mastery_states` is still materialized — scoped to the tenant and to the columns
the decay-based weak-topic/cohort rollups need. The decay model stays in JS for
determinism and explainability, and the output shape is byte-for-byte identical
(verified by the test suite).

```
OLD (load tables → JS): p50 41.40ms  mean 42.99ms
NEW (single SQL agg):   p50  1.96ms  mean  2.07ms      → 20.8×
```

This runs on **both** the main dashboard and the analytics page (every load),
and its old cost grew linearly with tenant size.

### 3. `getQuestionBankAnalytics` → SQL aggregates — **7.5× faster** + duplicate call removed

Was: call `getQuestionBank()` (multi-table join + full `assessment_items`
group-by) and discard the per-question stats, just to count statuses/sources/
flags. The analytics route *also* called `getQuestionBank()` separately, so the
heavy query ran **twice per request**. Now it is a handful of aggregates
(`count(*) filter`, `jsonb_array_elements_text` for flags) that never touch
`assessment_items`, and the duplicate is gone.

```
OLD (materialize bank + item group-by): p50 9.79ms  mean 10.12ms
NEW (SQL aggregates):                   p50 1.38ms  mean  1.36ms      → 7.5×
```

### 4. Caching for stable, non-student data (in-process, TTL + invalidation)

New `src/lib/cache.ts`. Cached: **subjects**, the **skill catalog**, the **model
registry**, and the **active classifier model**. Each is global, tiny, and
changes only on admin edits / retrains — invalidated explicitly on the relevant
writes (skill/question mutations invalidate the catalog; `save*` in the ML
registry invalidate the model caches), with a short TTL as a backstop.

- `loadClassifier` is called ~2×/answer on the hot assessment path; it now serves
  from memory, removing **2 DB round trips per answer** (~0.25ms each measured,
  plus 2 fewer pool acquisitions — the round-trip/connection saving matters more
  under concurrency than the raw latency).
- **Student-specific data is deliberately NOT cached** (mastery, assessments,
  student detail, recommendations, cohort snapshots) — caching per-learner data
  process-wide would risk staleness/leakage across users. This is enforced by
  keeping those functions uncached and documented in `cache.ts`.

**Why not Redis:** this is a single-process Next.js server and the cached
payloads are tiny and cheap to recompute, so a process-local `Map` beats Redis
(no network hop, no serialization, no ops cost) with no downside. Redis is only
justified once the app is scaled horizontally and needs *shared* invalidation —
at which point the `cached()/invalidate()` call sites can swap to a Redis client
(e.g. via a `CACHE_URL`) without touching callers. Until then, adding Redis would
be unjustified complexity.

### 5. Engine: remove redundant per-item query

`computeNextSessionQuestion` already loads the learner's full `mastery_states`
set for selection, but then called `loadSkillFeatures()` again (2 more queries)
just to read one skill's mastery for the chosen/pending item. That value is now
derived from the already-loaded set — **2 fewer queries per question served**, on
the interactive path a learner hits on every answer. `gradeItem` still uses
`loadSkillFeatures` (it genuinely needs the full feature vector).

### 6. Connection management

`src/db/index.ts` now sets explicit, env-tunable pool limits
(`DB_POOL_MAX`, `DB_POOL_IDLE_MS`, `DB_POOL_CONNECT_TIMEOUT_MS`) instead of the
pg defaults (max=10, **no acquire timeout**). The connection-timeout in
particular prevents a stuck/leaked connection from hanging a request
indefinitely; pool saturation is observable via `adaptiq_db_pool_connections`.

## Deliberately NOT changed (evidence-based restraint)

- **Client rendering / requests** — dashboards are React Server Components with
  no client-side polling or fetch loops (`grep` for `setInterval`/`fetch` in
  client components came back empty). No hydration or waterfall problem to fix.
- **`getQuestionBank` payload size** — it returns full question rows, but that is
  the actual data the questions dashboard renders; no evidence it is a
  bottleneck for its real use, so it was left alone (analytics simply stopped
  calling it).
- **Query-layer N+1** — the layer already avoids N+1 via `inArray` + `Promise.all`
  + lookup maps; no per-row query loops were found.
- **Selection scoring math** — kept in-memory and deterministic; the cost there
  was DB I/O (now addressed), not the arithmetic.

## Correctness

- Full suite: **269/269 tests pass** against real Postgres after all changes
  (schema/index changes applied via `drizzle-kit push`).
- `tsc --noEmit` clean; `npm run lint` clean except 3 pre-existing React
  component warnings unrelated to this work.
